## 设计约束

- 开发环境检查可在 macOS 运行并独立报告；生产目标检查必须拥有目标 Linux 实例的真实测量证据。
- Linux 必需检查失败、缺失或不支持时必须阻断对应生产门禁，不得静默 skip 或降级为 Mac 结论。
- `uv` 管理的 Python 3.12 是隔离运行时，不得替换系统 Python。
- 目标平台字段必须区分“设计目标”“候选值”“实际测量值”；公开镜像候选不等于已部署镜像事实。
- 结果状态为互斥枚举，按以下顺序判定：未开始测量（包括实例/凭据/工具缺失而无法开始）为 `NOT_RUN`；已开始但无法获得有效证据、来源/目标不匹配或缺独立验证为 `NOT_VERIFIED`；有效且绑定正确的测量证明必需约束不满足为 `FAIL`；有效证据完整、全部必需约束满足且独立验证通过才为 `PASS`。执行异常未取得可信测量不得伪装为能力失败或通过。
- `NOT_RUN` 记录包含环境类别、预期平台/目标、未执行原因；不得编造实际平台、测量时间或实例 ID。已执行结果必须绑定 `environment_class`、实际平台/架构、测量时间、命令来源、对象或实例标识和证据文件。缺任一必要绑定字段不允许 `PASS`。
- 每一类别以预先固定、非空的必需检查集合聚合；缺项按 `NOT_RUN` 处理。聚合优先级为 `FAIL` > `NOT_VERIFIED` > `NOT_RUN` > `PASS`；只有同类别、同目标的全部必需项均为 `PASS` 才得类别 `PASS`，空集合不允许通过。不同目标/版本的结果不得合并；新测量建新记录而不是覆盖历史。
- 聚合不可跨类别外推：`development_macos PASS` 不得生成 `target_linux` 或 `production_evidence PASS`。正式生产证据未开始时保持 `NOT_RUN`；已开始但目标 Linux 前置任一必需项为 `NOT_RUN`、`NOT_VERIFIED` 或 `FAIL` 时，生产资格不得通过，明确记录前置阻断理由。生产 PASS 还需要该生产环境自己的完整证据和正式门禁；目标 Linux PASS 本身不等于生产 PASS。本卡任何聚合结果均不得将 `production_ready` 置为 true。
- 测试/预生产环境属于独立的 `preproduction_linux` 类别，使用隔离数据与测试凭据；其 PASS 只能证明目标版本在隔离环境的候选验证，不等于正式 ECS `production_evidence` PASS，且生产凭据不得流入该环境。
- 变更保持薄适配层方向，不复制控制内核，不引入分布式组件。
