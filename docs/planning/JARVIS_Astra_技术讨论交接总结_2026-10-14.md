## 一、项目愿景与核心目标

JARVIS 是一个以《钢铁侠》中的贾维斯为长期参考的个人智能体工程。目标不只是聊天、调用工具或控制电脑，而是逐步实现：

1. **稳定的人格和行为逻辑：** 保持相对一致的性格、判断原则、沟通节制和交互习惯。
2. **可信长期记忆：** 长期保留重要事实和偏好，记录来源，支持纠错、撤回及必要的删除。
3. **自主理解和规划：** 理解长期目标，拆分任务，并根据实际情况调整未执行的计划。
4. **可靠行动：** 在授权范围内操作工具，正确处理不确定结果、重复请求、取消、故障与恢复。
5. **受控主动性：** 在合适的时间主动推进有价值的工作，同时避免越权和过度打扰。
6. **受控自我改进：** 发现能力缺口、提出方案、编写技能或工具，经独立评测后安全发布、回滚或停止。
7. **跨模型和设备连续性：** 尽量降低对某个模型、软件和设备的永久依赖。
8. **用户自主控制：** 重要数据、授权、运行和演进决策归用户掌控。
9. **长期运行：** 最终部署于云服务器，能够持续执行并具备可验证的故障恢复能力。

**重要边界：** 上述为长期愿景，不能将规划中的能力认定为当前已实现的能力。尤其不能将模型能够写代码，等同于已经实现可靠的自主进化。

## 三、为什么重新评估项目价值

成熟个人智能体和开源框架已经覆盖许多通用功能，如会话、工具、技能、定时任务、记忆及部分自动代码编写。因此，JARVIS 的价值不能简单建立在“别人不会、我们会”的功能数量竞争上。

需要验证的差异主要是三类：

- **可信行动：** 在故障、超时、重复请求、授权撤销和未知结果等情况下，仍能正确约束行动。
- **可信连续性：** 在会话中断、模型替换、升级或故障恢复后，保留有来源、可纠正的记忆及可核对的任务状态。
- **可信成长：** 能提出和实现新能力，但由独立、不可随意修改的评测与发布门禁决定是否采用。

这些都是**待验证的候选优势**，而不是已被证明优于其他产品的事实。

## 四、Astra 于 2026-10-13 的独立技术评审

**参考报告：** `JARVIS_INDEPENDENT_TECHNICAL_REVIEW_2026-10-13.md`。

### 4.1 工程成熟度判断

据 Astra 当时检查的特定代码基线：

- 正式 `src` 中有 **4 个 Python 文件、189 行物理行**。
- 隔离回归 **273 项测试通过**，但大量测试属于契约、状态枚举、数据结构或证据分类验证。
- K0 尚未形成产品级可靠任务执行闭环。
- K1–K4 尚无相应完整产品级运行系统。
- 规划中的核心执行不变量尚不能被视为已在产品中实现。

**解释：** 规划和契约审查的成熟度显著领先于实际可运行的个人智能体；测试数量不代表用户功能完成度。

### 4.2 重要架构路线选择

Astra 发现，正式项目更接近独立确定性执行内核，尚未有完整的 Hermes 适配与集成实现。由此提出两条候选路线：

- **路线 A：** 自研完整智能体基础设施及可靠执行内核。
- **路线 B：** **Hermes + 有限 JARVIS 控制层**：由 Hermes 提供成熟的模型、会话、技能和普通规划能力；由 JARVIS 掌握授权、任务状态、副作用身份、结果核对、可信记忆、独立改进评测与发布边界。

Astra 更倾向路线 B，但明确指出它仍需通过**工具出口覆盖、操作系统隔离、故障恢复与真实任务对照实验**证明可行，不能靠中间件回调或提示词自律假定安全。

### 4.3 K0 中值得保留的设计

- 稳定的 Task / Operation Intent / Attempt 身份与历史。
- 稳定的 Operation Key 和副作用去重。
- 未知结果先核对，不盲目重试。
- 明确的取消、急停、授权撤销与执行竞争语义。
- 外部效果独立核验、可靠持久化、崩溃恢复。
- 不以“数据库已提交”推导“远端操作必然恰好执行一次”。

Astra 建议**缩小首个可运行切片的通用化范围**，而不是降低关键安全和正确性标准。

### 4.4 两个具体技术问题

1. **Reconciliation 决策语义：** 当前候选 Schema 可以让 `CONFLICTING_EFFECT_PRESENT` 与 `RETRY_SAFE` 同时通过结构校验。需要有受测试的纯决策校验器，并确保执行器实际调用。该发现不代表已发生生产事故。
2. **取消与 dispatch 的竞争：** 必须定义取消的准确生效点，处理已经发出的外部请求，以及重启后的未知结果。不能仅凭一个取消标志推定远端效果可撤回。

### 4.5 自我改进的现实边界

当前工程技术可以支持：有限任务的故障归因、候选方案研究、受限代码生成、独立测试、版本绑定、分阶段发布及回滚。

尚不足以保证：开放任务的持续单调变强、任意核心自主修改后仍绝对安全、永久人格一致以及无限期无人监督安全。

**最困难的环节不是产生代码，而是正确评价改进、抵抗对评测的迎合，并在升级及回滚后保持权限、记忆和任务连续性。**

### 4.6 Astra 的最终建议

**继续 JARVIS，但优先验证 Hermes + 小型受控执行层、可信中文记忆及真实个人任务价值。** 原报告仅为决策输入，不批准代码重构或规划修改。

## 五、随后安排的 Sol 独立架构实验

**实验名：** JARVIS Hermes 集成架构与最小可靠执行闭环验证。  
**实验目录：** `仓库根/docs/experiments/20261013-hermes-k0/`。  
**报告日期：** 2026-10-14。

### 5.1 实验的两个问题

- **实验 H1：** Hermes 的实际工具路径是否可被受限 JARVIS 控制层可靠约束，且不能轻易绕过。
- **实验 H2：** 持久化身份、授权、Intent、核对和恢复能否在指定工具契约下产生额外的可靠性收益。

**注意：** 此实验对 H1/H2 的编号定义不同于早期 Astra 报告中同名假设，不应混淆。

### 5.2 Sol 报告中的结果

**总体结果：`PARTIAL`（部分通过）。**

- **77 项检查通过，0 项失败**（系报告与测试记录声明）。
- 三种合成工具契约的正常授权执行通过。
- 受限环境中的部分原生终端、文件、插件、Cron 脚本及子进程出口获得拒绝未经授权写入的证据。
- 本机进程终止、超时、丢响应、重复调用、取消/撤销/停止竞争等测试有相应证据。
- 未验证完整浏览器、真实外部工具服务器、原生模型子代理、调度器外部投递及完整真实模型智能体循环。
- 未进行真实大模型对照、长期人工成本评估、Linux/ECS 生产持久化及完整独立复评。

### 5.3 A/B 对照结果及适用边界

| 场景                | A：Hermes 固定工具层基线 | B：增加 JARVIS 控制层  |
| ----------------- | ---------------- | ---------------- |
| 文件请求重放 3 次        | 产生 1 个文件，后续冲突    | 产生 1 个文件，复用原验证状态 |
| 支持幂等键的服务请求重放 3 次  | 1 个效果            | 1 个效果            |
| 不支持幂等键的服务请求重放 3 次 | 3 个效果            | 1 个效果            |
| 幂等服务丢响应后显式重复      | 1 个效果            | 1 个效果并独立核对       |
| 不可幂等服务丢响应后显式重复    | 2 个效果            | 1 个效果，进入阻塞待人工核对  |

**严格解释：** A 组的重复请求由实验驱动器主动发出，不能据此宣称 Hermes 在真实使用中会自动盲重试。A 组也可以保守暂停未知请求，因此 B 组已被实验证明的增量主要是**跨调用的持久操作身份和恢复规则**。本次没有真实模型调用，不支持比较完整自然语言任务完成率、模型成本或总体产品优劣。

## 七、尚未解决的关键技术问题

### 7.1 完整 Hermes 智能体调用链

是否可以让真实 Hermes 模型完成：理解任务、制定计划、提出受控操作、经过授权执行、接收结果、处理失败并继续任务？

尚未充分验证真实模型重规划、上下文压缩、原生子代理、浏览器/外部工具、调度投递等路径。

### 7.2 执行控制的不可旁路性

是否存在终端、插件、浏览器、外部工具或子进程能够直接获得业务写权限，绕过控制层？中间件异常时是否仍能由操作系统和凭据边界保证拒绝未经授权的副作用？

### 7.3 稳定操作身份与语义重复

同一个 Operation Key 可以防止同身份请求重复执行，但模型把同一业务效果改写为另一段文本、重新规划并生成不同身份时，仍可能造成**语义重复**。K1/K0 集成必须正面验证。

### 7.4 实际云端可靠性

需要在符合目标部署要求的 Linux 环境验证服务进程、文件系统同步、持久化、权限、恢复和故障注入；本地 SIGKILL 不能等同于真实断电。

### 7.5 个人任务的净价值

必须比较 Hermes 原生方案与增加控制层后的方案在**实际授权任务完成率、误报、恢复、人工介入、延迟、模型成本和维护成本**上的净收益，而不是只比较模拟去重场景。

## 八、阶段性共识与决策纪律

1. **不降低最终理想。** 仍追求长期记忆、稳定人格、可信行动、主动性及受控自我改进。
2. **不把现有设计当作永远正确。** 可以提出更简单或更有效的方法，但重要变化应基于证据。
3. **不因为新报告就立即重构。** Astra 的评审和 Sol 的实验都是决策输入，不能自动修改正式规划或任务完成状态。
4. **保留有价值的 K0 契约。** 稳定操作身份、核对、权限、取消和恢复等不能为追求速度而直接放弃。
5. **复用成熟基础设施。** 如果 Hermes 已经可靠提供某项通用能力，应优先比较复用价值，避免无意义地重复研发。
6. **避免继续停留在纯文档阶段。** 以最小可运行切片、可复现故障实验和真实个人任务推进设计收敛。
7. **区分验证层级。** 静态检查、隔离原型、完整智能体、目标 Linux 环境及生产验收不是一回事。
8. **保持开发连续性。** 不覆盖历史审计、有效代码和任务状态；正式变更遵守工程治理与授权规则。
